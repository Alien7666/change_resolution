# Go Display Tray 重構設計

## 目標

將現有 Python 解析度切換腳本重構為 Windows-only 的 Go 系統匣工具。工具只控制指定的 Mi Monitor 顯示模式，不啟動、不注入、不掛勾 VALORANT，也不讀寫遊戲檔案；使用者可以隨時手動切換 4:3，並在遊戲關閉後自動恢復原始解析度。

## 使用者流程

1. 啟動工具時只讀取並顯示目前狀態，不變更任何螢幕。
2. 使用者開啟「使用 4:3」時：
   - 以硬體 ID `MONITOR\\XMI27B2` 找到 Mi Monitor 對應的 `\\\\.\\DISPLAYn`。
   - 保存當下完整的桌面排列（每台顯示器的模式與座標）。
   - 驗證並套用 `1920×1440 @ 180 Hz`，同時平移其他顯示器讓桌面保持連續。
   - 將視窗隱藏至 Windows 系統匣。
3. 4:3 啟用期間，使用者可隨時關閉開關；工具會取消尚未執行的自動恢復計時，並立即恢復先前保存的模式。
4. 4:3 啟用後，工具只觀察 `VALORANT-Win64-Shipping.exe` 是否曾出現在 Windows 程序清單中。程序由存在轉為不存在時，等待 3 秒後恢復原始模式。
5. 退出工具時若仍由本工具啟用 4:3，先恢復原始模式再退出。

工具不負責啟動 VALORANT，也不會因偵測到遊戲啟動而切換解析度。若 4:3 啟用後遊戲從未出現，解析度維持不變，直到使用者手動關閉 4:3 或退出工具。

## 技術選擇

- Go 1.27.x，目標平台 `windows/amd64`。
- `golang.org/x/sys/windows` 呼叫 Windows API。
- `github.com/lxn/walk` 建立原生 Windows 視窗與通知區圖示。
- `ChangeDisplaySettingsExW` 明確指定顯示裝置。
- `CreateToolhelp32Snapshot` 與 `Process32FirstW` / `Process32NextW` 只列舉程序名稱。
- Windows GUI subsystem 建置，成品為單一 `.exe`，不顯示主控台視窗。

Walk 適合此 Windows-only 小工具，能提供原生控制項與系統匣功能，且不需要 Wails 的 WebView/前端工具鏈，也不需要 Fyne 的 CGO/C 編譯器。

## 元件與邊界

### 顯示控制

`DisplayController` 負責列舉顯示裝置、以硬體 ID 對應目標螢幕、讀取目前模式、讀取整體桌面排列（每台顯示器的模式、座標與是否為主要顯示器）、驗證目標模式，以及逐台依序套用與恢復整體排列（含失敗回復與套用後驗證）。

第一版預設設定：

- 顯示器硬體 ID 前綴：`MONITOR\\XMI27B2`
- 4:3 模式：`1920×1440 @ 180 Hz`、32 bpp
- 原始模式與原始排列：啟用 4:3 當下動態擷取，不硬編碼；只有在無法取得已保存模式時，GUI 才提供明確的 `2560×1440 @ 180 Hz` 緊急恢復動作（該動作同樣會重新規劃排列，避免較寬的模式壓到鄰居）。

套用前先以 `CDS_TEST` 測試模式；正式套用不使用 `CDS_UPDATEREGISTRY`，避免將暫時遊戲模式永久寫入使用者設定。

其他顯示器的解析度、刷新率與色彩深度永遠不變；唯一會被寫入的是桌面位置。目標寬度改變後，若其他顯示器留在原座標，桌面會出現滑鼠無法跨越的空隙，因此啟用 4:3 時會依寬高差平移目標之後的顯示器，使桌面保持連續：

- 位移量為目標模式的寬（高）差；座標大於目標的顯示器同向平移。
- Windows 要求主要顯示器（primary）位於 `(0,0)`，因此平移後整體再校正回原點；目標本身即為主要顯示器時，目標永遠不動。
- 只有目標會寫入模式欄位，其餘顯示器只宣告 `DM_POSITION`。

整體排列以「逐台依序套用」的方式寫入：每台顯示器各自一次 `ChangeDisplaySettingsExW(裝置, &DEVMODEW, CDS_FULLSCREEN)`。不使用 `CDS_NORESET` 暫存加單次提交的交易寫法，原因記錄在「錯誤與恢復」一節。逐台套用本身沒有原子性，因此由程式補上三件事：

- **順序**：桌面中途出現空隙無害，中途重疊有害（Windows 會自行重排）。目標在兩個軸向都沒有變大時，先套用目標的模式讓出空間，其餘顯示器再平移過來補上；目標在任一軸向變大時，先平移其餘顯示器讓出空間，最後才套用目標的模式。判斷依據是規劃出的尺寸與驅動回報的目前尺寸，不是寫死的解析度。
- **失敗回復**：套用過程中記住每台顯示器原本的座標與模式；任何一次呼叫失敗，就把已經改過的顯示器（由新到舊）改回去，再回報原始錯誤。若回復本身也失敗，回報的訊息會明確指出桌面被留在套用到一半的狀態，而不是假裝什麼都沒變。
- **套用後驗證**：最後一次成功呼叫之後重新讀取整體排列並與計畫比對。與計畫不符即視為錯誤（理由見「錯誤與恢復」），不會把「讀不到或位置不對的螢幕」當成成功。

若無法算出安全排列（顯示器會重疊、有顯示器讀取失敗、主要顯示器會被移動），則不做任何變更並回報錯誤。

啟用 4:3 當下保存的是**完整排列**（每台顯示器的裝置名稱、模式與座標），恢復時一併還原：目標回到保存的模式，其餘顯示器回到保存的座標並保留自己目前的模式。

### 程序觀察

`ProcessWatcher` 每秒以 Toolhelp snapshot 列舉一次程序名稱，不取得 VALORANT 程序控制代碼、不讀取程序記憶體，也不與 Vanguard 或遊戲視窗互動。

只有在本工具成功啟用 4:3 後才建立觀察狀態：

- 尚未看見遊戲：不動作。
- 看見遊戲：記錄本次執行已開始，不變更顯示模式。
- 遊戲消失：啟動可取消的 3 秒恢復計時。
- 計時期間遊戲重新出現：取消恢復。
- 使用者手動關閉 4:3：取消觀察與計時，立即恢復。

### 應用程式狀態

核心狀態機與 GUI 分離，狀態包含：

- `Native`：未由工具套用 4:3。
- `Applying`：正在驗證並套用 4:3。
- `ActiveWaitingForGame`：4:3 已啟用，尚未觀察到遊戲。
- `ActiveGameRunning`：4:3 已啟用且遊戲正在執行。
- `RestorePending`：遊戲已關閉，等待 3 秒。
- `Restoring`：正在恢復。
- `Error`：操作失敗，保留可恢復的狀態與錯誤訊息。

所有耗時操作在背景 goroutine 執行；GUI 更新切回 Walk UI 執行緒。解析度切換操作序列化，避免快速重複點擊造成競爭。

### GUI 與系統匣

主視窗保持精簡：

- Mi Monitor 是否已找到。
- 目前解析度與刷新率。
- 「使用 4:3（1920×1440 @ 180 Hz）」開關。
- 目前狀態或錯誤訊息。
- 「隱藏至系統匣」與「恢復 2K」按鈕。

關閉主視窗只隱藏至系統匣。系統匣選單包含：

- 顯示主視窗。
- 使用 4:3。
- 恢復原始解析度。
- 結束。

若目標螢幕不存在或目標模式不受支援，停用 4:3 開關並顯示原因，不變更其他螢幕。

## 可擴充性

硬體設定放在 `DisplayProfile`：

```text
Name
MonitorHardwareID
GameMode
FallbackNativeMode
ProcessName
RestoreDelay
```

第一版只內建一個 Mi Monitor profile，但顯示控制與 GUI 不依賴固定的 `DISPLAY1`。未來加入螢幕與解析度選擇器時，只需提供多個 profile 或設定儲存，不更動 Win32 顯示控制與核心狀態機。

## 錯誤與恢復

- 找不到螢幕：保持現況並顯示錯誤。
- 無法算出安全排列（顯示器會重疊、有顯示器讀取失敗、主要顯示器會被移動）：不做任何變更並顯示錯誤。
- 恢復時顯示器編號已改變、保存排列不再對應目前桌面：中止恢復並顯示錯誤，保留 4:3 的擁有權讓使用者修正後重試。
- 目標模式測試失敗：不套用模式。
- 套用失敗：顯示 Win32 錯誤／`DISP_CHANGE_*` 結果。
- 不使用 `CDS_NORESET`：MSDN 記載 `CDS_NORESET` 只在與 `CDS_UPDATEREGISTRY` 併用時才有意義，而本工具禁用 `CDS_UPDATEREGISTRY`；實測在目標機器（RTX 3070、四螢幕、`\\.\DISPLAY1` 為 2560×1440@180 的主要顯示器）上，以相同的目前設定原值回寫、只改旗標字時的結果為：`CDS_FULLSCREEN|CDS_NORESET` → `DISP_CHANGE_BADFLAGS`、`CDS_NORESET` → `DISP_CHANGE_BADFLAGS`、`CDS_FULLSCREEN` → `DISP_CHANGE_SUCCESSFUL`、旗標為 `0` → `DISP_CHANGE_SUCCESSFUL`。暫存呼叫在這台機器上根本無法通過，交易寫法等於功能完全失效，因此改為逐台依序套用。
- 套用中途失敗：把已經改過的顯示器改回原本的座標與模式，再回報造成失敗的 Win32 錯誤；4:3 的擁有權與可重試性不變。
- 失敗回復本身又失敗：回報為「桌面被留在套用到一半的狀態」的獨立錯誤，訊息同時帶出原始失敗與回復失敗，讓使用者知道螢幕確實被動過；剩下的顯示器仍會繼續嘗試回復，盡量減少停在錯誤位置的螢幕數。
- 套用後排列與計畫不符（Windows 自行重排、某台顯示器讀不回來）：視為錯誤。工具只能證明顯示器互不重疊，無法證明滑鼠到得了每一台，因此不把「看起來還算連續」當成成功；此時不再自動改動桌面，改由恢復流程依目前實際桌面重新規劃。
- 恢復失敗：保留「恢復 2K」動作，並在系統匣顯示錯誤通知。
- 工具正常退出：盡力恢復由本次執行保存的原始模式。
- 工具或系統非正常終止：無法保證執行清理；因不使用 `CDS_UPDATEREGISTRY`，不永久寫入暫時模式。再次開啟工具時不自動改變顯示模式，以符合「啟動不做任何動作」要求。

程式不承諾顯示模式實際切換時零黑屏；目標是讓切換只發生在手動啟用、手動關閉或遊戲結束後恢復三個時點，並避免 VALORANT Alt+Tab 觸發不同桌面模式的往返切換。

## 測試策略

- 狀態機使用假的 DisplayController、ProcessWatcher 與可控制時間的 timer 做單元測試。
- 驗證手動開啟、手動關閉、遊戲從未出現、遊戲結束延遲恢復、延遲期間重開遊戲、退出恢復與錯誤路徑。
- Win32 結構轉換與程序名稱比對使用純函式測試。
- Windows integration test 只做 `CDS_TEST` 與唯讀列舉，預設測試不得實際改變使用者解析度。
- 排列計算為純函式：以實測的四螢幕座標驗證縮窄後桌面連續、其他螢幕只有位置改變、主要顯示器不動、恢復可完整還原座標，以及無法安全排列時中止。
- Win32 邊界以假的 `user32` 驗證呼叫序列：目標縮小與放大兩種情境下的逐台套用順序、每次呼叫都帶 `CDS_FULLSCREEN` 且都不帶 `CDS_UPDATEREGISTRY`、中途失敗會把先前的顯示器改回去並回報原始錯誤、回復失敗會被獨立回報、套用後排列與計畫不符會被抓出來、非目標顯示器的 `dmFields` 恰好只有 `DM_POSITION`，以及 `CDS_TEST` 仍是第一個跨入 Win32 的呼叫。
- 發布前人工 smoke test 才在 Mi Monitor 上實際切換，確認另外三台螢幕的解析度與刷新率未被修改、桌面沒有空隙或重疊，且恢復後座標與原本相同。

## 專案整理

Go 版本達成功能對等並完成驗證後，刪除舊 Python 腳本、PyInstaller spec、已提交的 `build/` 與 `dist/` 產物，以及本次工作區內對應的未追蹤舊產物。加入 `.gitignore`，避免再次提交編譯輸出。

不修改使用者電腦上的 VALORANT 設定、Riot Client、Vanguard 或 NVIDIA 控制台設定。
