# 可設定 Profile 設計

## 目標

把目前寫死在 `domain.DefaultProfile()` 的一組硬體設定——顯示器 `MONITOR\XMI27B2`、遊戲模式 `1920×1440 @ 180 Hz`、備援 `2560×1440 @ 180 Hz`、觀察程序 `VALORANT-Win64-Shipping.exe`——改成由使用者自己決定。**目標顯示器、目標顯示模式、觀察的程序**三者皆可設定，設定持久化到檔案並在重啟後仍然有效，且第一次執行的使用者不必用文字編輯器碰任何檔案就能走到可用的狀態。

現有 spec（`2026-09-13-go-display-tray-design.md`）的所有承諾一字不變，並在本文件中被視為前提：

- 啟動只讀取與顯示狀態，永遠不主動變更任何顯示模式。
- 永遠不使用 `CDS_UPDATEREGISTRY`；套用任何模式之前一定先做 `CDS_TEST` 前置驗證。
- 不取得遊戲程序控制代碼，只用 Toolhelp 列舉執行檔名稱做比對。
- 不啟動、不注入、不掛勾遊戲；不碰 Riot / Vanguard / 遊戲檔案。
- 其他顯示器的解析度、刷新率與色彩深度永遠不在寫入集合內，只有桌面座標會為了讓桌面保持連續而平移；主要顯示器固定在 `(0,0)`。
- 由本工具套用的模式，在手動關閉、被觀察的程序結束後、以及工具退出時都會恢復。

一般化會讓其中幾條承諾更難兌現（尤其是 `CDS_TEST` 的通過率），這一點另闢「與既有約束的新張力」一節誠實交代，不藏在細節裡。

## 不在範圍內

- **GPU 縮放控制。** 非原生比例（例如 16:9 面板上的 `1920×1440`）需要在顯示卡層級開啟全螢幕縮放，目前 README 要求使用者到 NVIDIA 控制台手動設定一次。目前有一支獨立的 NVAPI spike 在評估能否由工具代為讀取／設定，它會有自己的 spec 章節。本設計只做一件相關的事：在使用者挑到與面板原生比例不同的模式時提醒他這項前置設定存在；工具本身不讀、不寫、不假設任何 GPU 縮放狀態。
- 多組 profile／每個遊戲一組設定（見「未解問題 8」，版本化機制已為它留路）。
- 同時觀察多個程序。
- 同時管理兩台以上顯示器。
- 全域快捷鍵。
- 由工具產生驅動未列舉的自訂解析度（「解析度選擇」有一節說明要做的話得付什麼代價，第一版不做）。
- 單一執行個體鎖。兩份工具同時執行會各自管理顯示狀態並互相覆蓋設定檔；設定檔寫入是原子的且只發生在使用者按儲存時，所以最壞情況是後寫者贏，不會產生半份檔案。真正的互斥（`CreateMutexW` 具名互斥）值得做，但屬於另一件事。

## 設定模型

### profile 現在包含什麼

`domain.Profile` 從「內建常數的載體」變成「使用者擁有的設定」。欄位與現在幾乎同名，但每一個的來源都改變了：

| 欄位 | 來源 | 必要性 |
|---|---|---|
| `Monitor` | 使用者從偵測到的顯示器清單中挑選 | 必要 |
| `GameMode` | 使用者從該顯示器列舉出的模式中挑選 | 必要 |
| `FallbackMode` | 未設定時於使用當下由列舉結果推導 | 選用 |
| `ProcessName` | 使用者從執行中的程序名稱挑選或自行輸入 | 選用 |
| `RestoreDelay` | 使用者輸入，預設 3 秒 | 選用 |
| `Label` | 挑選當下記下的顯示器友善名稱，僅供顯示 | 選用 |

兩個值得單獨說明的變化：

- **`FallbackNativeMode` 不再是使用者要填的欄位。** 目前寫死的 `2560×1440 @ 180 Hz` 只對一台機器成立。改為：未設定時，於需要用到的當下取「該顯示器列舉出的像素數最大的解析度，並取該解析度下最高的刷新率」。GUI 的按鈕文字直接印出算出來的數字，使用者按下去之前就知道自己會拿到什麼；推導不出來（例如列舉失敗）就停用該按鈕並寫出原因，而不是退回某個猜測值。
- **schema 裡沒有、也不會有「啟動時自動套用」這個鍵。** 這不是疏漏。「啟動不改變任何螢幕」是這個工具的安全邊界之一，加上那個鍵會讓它變成另一個工具，需要另一份 spec。

型別草圖（示意，不是實作）：

```go
type MonitorIdentity struct {
	InstancePath   string // 主鍵：裝置介面路徑
	HardwareID     string // 次鍵：MONITOR\XMI27B2
	ModelWasUnique bool   // 挑選當下，這個 HardwareID 是否只對到一台
	Label          string // 僅供顯示，永不參與比對
}
```

### 顯示器身分：讓它撐過重開機、換線與重新編號

`\\.\DISPLAYn` 是 Windows 的動態編號，不能存進設定檔：重開機、換接線順序、拔掉一台螢幕都會讓它換人。現有的硬體 ID 前綴比對（`strings.HasPrefix` 到 `EnumDisplayDevicesW` 回報的 `DeviceID`）比編號穩，但它識別的是**型號**，不是**那一台**。兩台同型號的顯示器會同時命中，而 `ResolveTarget` 現在的做法是回傳第一個命中——也就是安靜地挑一台。這在只有一台 Mi Monitor 的桌面上從來不會出錯，一般化之後就是個等著咬人的 bug。

改為三層身分階梯，由精確到寬鬆，任何一層都不容許「猜」：

1. **裝置介面路徑（主鍵）。** 以 `EnumDisplayDevicesW(..., EDD_GET_DEVICE_INTERFACE_NAME)` 取得顯示器的 `DeviceID`，形如
   `\\?\DISPLAY#XMI27B2#5&2b9d4d4&0&UID4357#{e6f07b5f-...}`。
   其中 `UID4357` 這一段對應顯示卡的輸出埠，所以這個字串能區分兩台同型號的顯示器。比對方式是**整串、不分大小寫的完全相等**。它撐得過重開機與 Windows 重新編號 `\\.\DISPLAYn`；撐不過把線換到另一個埠——那會換一個 UID。
2. **硬體 ID（次鍵，有條件）。** 主鍵對不到時，才用 `MONITOR\XMI27B2` 這一層比對，而且只在**恰好命中一台**時採用。這條路徑是為了換線／換顯示卡埠而存在的復原機制。
   關鍵限制：只有當設定檔記錄了 `ModelWasUnique = true`（挑選當下這個型號在這台機器上只有一台）才啟用這一層。如果使用者設定時就有兩台同型號，次鍵永遠被停用——因為此時「只命中一台」很可能表示另一台正在睡眠或被拔掉，而不是表示這就是他要的那一台。寧可請使用者重選，也不要把模式套到另一台螢幕上。
3. **都對不到，或對到多台：不動作。** 見「驗證與失敗」。

**兩台同型號顯示器的具體結局：** 設定時兩台都會出現在清單裡，各自帶著自己的裝置介面路徑、`\\.\DISPLAYn` 與友善名稱，使用者挑的是其中一台的路徑，`ModelWasUnique` 記為 `false`。之後每次解析都用完全相等比對，兩台同時在線也只會命中被選的那一台。把線對調過之後，主鍵會對不到（UID 變了），次鍵被停用，工具停用 4:3 切換並請使用者重選——這是誠實的失敗，不是把遊戲模式套到隔壁那台螢幕上。EDID 序號可以進一步把這個情境救回來，但那是登錄檔讀取且不是每台顯示器都填了唯一序號，列在「未解問題 7」。

另外兩條規則落在同一層：

- 解析之後拿到的 `\\.\DISPLAYn` 是**顯示卡的 adapter**，也是 `ChangeDisplaySettingsExW` 與 `EnumDisplaySettingsW` 真正接受的名字。在一般的延伸桌面下一台顯示器對一個 adapter，但**複製／鏡射模式**下一個 adapter 會驅動多台顯示器。此時工具無法只改其中一台，因此規則是：解析出來的 adapter 若還掛著另一台在線的顯示器，直接拒絕並寫出原因。
- 友善名稱（給人看的「Mi Monitor 27」而不是「Generic PnP Monitor」）與比對完全無關。它只影響 UI 文字，來源見「未解問題 5」。

### 檔案位置

```
%APPDATA%\ResolutionTray\config.json
```

展開後即 `C:\Users\<使用者>\AppData\Roaming\ResolutionTray\config.json`（Go 的 `os.UserConfigDir()` 在 Windows 上回傳的就是 `%AppData%`）。測試與開發以環境變數 `RESOLUTION_TRAY_CONFIG` 覆寫整個路徑，所以自動測試永遠不會碰到使用者真正的那一份。

**為什麼不放在 exe 旁邊：**

- Release 是單一免安裝執行檔，使用者通常直接放在 `Downloads`，也可能放進 `Program Files`。後者沒有管理員權限就寫不進去，而這個工具明確不要求提權。
- 更糟的是它會**看起來**寫得進去：UAC 虛擬化會把寫入 `Program Files` 的動作靜默導向 `%LOCALAPPDATA%\VirtualStore\...`，使用者打開他以為的那份檔案編輯，工具卻在讀另一份。這正是「絕不半懂地套用設定」要排除的情境。
- 升級方式是覆蓋或另存新檔；設定放旁邊會在換檔案時失聯，或被留在舊資料夾裡。
- 同一台機器上的不同 Windows 使用者會共用同一份檔案，互相覆蓋彼此的顯示器設定。
- 從 USB 或網路磁碟執行時，寫入位置與可寫性都不可預期。

`%APPDATA%` 是 Roaming，在有網域漫遊設定檔的環境下會跟著使用者跑到別台機器，而顯示器身分是機器相關的。這不會造成損害——到了另一台機器上主鍵對不到，走的就是「找不到顯示器」那條路：停用切換、說明原因、請使用者重選——但它是選 `%LOCALAPPDATA%` 的唯一理由，列在「未解問題 1」。

### 格式

JSON，UTF-8（不寫 BOM），LF，寫出時縮排兩個空白。選它的理由是標準函式庫就有、使用者用記事本打得開、而且不必為了設定檔多拉一個相依套件。代價是 JSON 沒有註解，緩解方式是**讀取時忽略不認識的鍵**，所以使用者自己加的 `"_comment"` 之類的鍵不會讓檔案壞掉。

```json
{
  "version": 1,
  "monitor": {
    "instancePath": "\\\\?\\DISPLAY#XMI27B2#5&2b9d4d4&0&UID4357#{e6f07b5f-ee97-4a90-b076-33f57bf4eaa7}",
    "hardwareId": "MONITOR\\XMI27B2",
    "modelWasUnique": true,
    "label": "Mi Monitor 27"
  },
  "gameMode": { "width": 1920, "height": 1440, "refreshHz": 180, "bitsPerPixel": 32 },
  "fallbackMode": null,
  "watch": {
    "processName": "VALORANT-Win64-Shipping.exe",
    "restoreDelaySeconds": 3
  }
}
```

**寫入是原子的。** 寫到同目錄的 `config.json.tmp`、`Sync()`、再 `os.Rename` 蓋過去。同目錄是必要條件，跨磁碟的 rename 不是原子操作。永遠不原地截斷後重寫——那個做法在中途斷電時留下的是一份長度為零的設定檔。

**只有三件事會寫檔：** 使用者在設定對話框按下儲存；次鍵重新對應成功後回寫新的 `instancePath`（見「未解問題 4」）；以及使用者明確選擇「重新設定」時把讀不懂的舊檔改名保留。除此之外——尤其是在讀取或驗證失敗的任何路徑上——一個位元組都不寫。

### 版本化

`version` 是必要的整數，放在檔案第一個鍵。目前值為 `1`。

- **加欄位不升版。** 缺席的選用欄位一律解讀為「使用文件記載的預設值」，而且**不會因為補了預設值就把檔案重寫回去**。這條規則就是「未來新增欄位不會弄壞既有使用者檔案」的全部內容。
- **只有會讓舊檔案產生不同語意的改動才升版。** 例如把單一 profile 改成多組 profile、或改變某個既有欄位的單位。
- **`version` 比本版新：拒絕，並且不寫檔。** 工具進入唯讀狀態，畫面明說「這份設定檔是較新的版本寫的」，切換被停用。降級執行不得把新格式重寫成舊格式——那是資料遺失，不是相容性。
- **`version` 比本版舊：在記憶體中遷移後照常使用。** 遷移結果只在使用者下一次按儲存時才落地，落地前先把原檔複製一份為 `config.v<舊版本>.bak`。
- **不認識的鍵：讀取時忽略。** 同一個版本內的 schema 是封閉的，所以下一次儲存會把它們丟掉；真正需要保留未知鍵的情境是「較新版本寫的檔」，而那條路徑本來就完全不寫檔，所以不會發生遺失。

## 驗證與失敗

設定檔是一個使用者拿文字編輯器就能改的邊界，因此照不可信輸入處理。兩條總規則先講，其餘都是它們的實例：

> **一份設定檔要嘛被完整理解並使用，要嘛完全不被使用。沒有部分載入。**
>
> **任何超出範圍的值都是拒絕，不是夾擠（clamp）到範圍內。** 夾擠是在沒有告知使用者的情況下改寫他的意思。

| 情況 | 規則 |
|---|---|
| 檔案不存在 | 不是錯誤。走首次啟動流程。 |
| 無法讀取（權限、I/O） | 拒絕。唯讀狀態，顯示完整路徑與底層錯誤，保留「重新讀取」。不寫檔。 |
| 不是合法 JSON | 拒絕。把 `json.SyntaxError.Offset` 換算成行列並一起顯示。**不修復、不重寫。** |
| 缺 `version`／`version` 不是整數 | 拒絕。這是檔案損毀，不是舊版檔案。 |
| `version` 大於本版 | 拒絕（見上節）。 |
| 必要欄位缺席（`monitor`、`gameMode`） | 拒絕，指名是哪個欄位。 |
| 數值為負數或小數 | 拒絕。所有數值欄位都解到無號整數型別，所以 `-1` 與 `1.5` 天然是解析錯誤，不會被靜默截斷。 |
| 解析度數值不合理（0，或超出 `display/layout.go` 既有的 `maxDimension = 1<<16`） | 拒絕。 |
| `refreshHz` 為 0、1 或大於 1000 | 拒絕。0 與 1 在 DEVMODE 語意中是「硬體預設」，不是使用者的選擇。 |
| `bitsPerPixel` 不是 32 | 拒絕。工具只套用 32 bpp（缺席時預設 32）。 |
| `restoreDelaySeconds` 不在 0–60 | 拒絕，不夾擠。 |
| 找不到對應的顯示器 | **不是設定檔錯誤。** 保留設定，停用所有會變更顯示的控制項，顯示記下的顯示器名稱與「目前找不到」，「重新整理」保持可用。行為與現在的 `ErrTargetNotFound` 完全一致——螢幕會睡眠、會被切到別的輸入源。即使目前只接了一台螢幕也**不自動改綁**。 |
| 命中多台顯示器 | 拒絕解析（新的 `ErrTargetAmbiguous`）。列出每一台的 `\\.\DISPLAYn` 與介面路徑，請使用者重選。永遠不取第一個。 |
| 解析出的 adapter 還掛著另一台在線顯示器（複製／鏡射） | 拒絕。工具無法單獨改動其中一台。 |
| 顯示器列舉不出設定的模式 | 停用切換並說明「這台顯示器目前沒有回報 `1920×1440 @ 180 Hz`」，引導到設定對話框。設定檔保持原狀——顯示器換了輸入源或驅動更新之後模式可能又回來。 |
| `processName` 缺席、為空字串、或只有空白 | **合法**：解讀為「不觀察任何程序，只有手動切換，沒有自動恢復」。這個狀態必須在主視窗與系統匣提示中明講（「自動恢復：未設定」），不能讓使用者以為他設了卻沒生效。（見「未解問題 3」的替代方案。） |
| `processName` 是路徑而不是純檔名（含 `\` `/` `:`），或含 `<>"?*` 與直線分隔字元或控制字元，或是 `.` / `..`，或長度超過 255 | 拒絕整份檔案。理由不是潔癖：Toolhelp 回報的是純執行檔名稱，`matchesExecutable` 做的是完全相等比對，一個帶路徑的值**永遠不可能命中**。它會看起來設好了卻永遠不觸發，這比明確報錯糟得多。 |
| `processName` 沒有 `.exe` 副檔名 | 接受。Toolhelp 回報的是映像檔實際的名字，強制副檔名只會擋掉合法但少見的情況。 |

拒絕之後的使用者出路，全部是明確動作，沒有一個是自動的：**重新讀取**（改完檔案後不必重開工具）、**開啟設定檔所在資料夾**、以及**重新設定**——後者會先把讀不懂的檔案改名為 `config.bad-<時間戳>.json` 保留下來，再開啟設定精靈，而且只在使用者按下確認後才做。

## 解析度選擇

現在的程式碼從來沒有問過顯示器「你支援哪些模式」——`EnumDisplaySettingsW` 只被用來以 `ENUM_CURRENT_SETTINGS`（`0xffffffff`）讀目前設定。一般化之後這是第一步。

### 列舉

以 adapter 名稱（`\\.\DISPLAYn`）從索引 0 開始呼叫 `EnumDisplaySettingsW(device, i, &dm)`，`i` 遞增到回傳 `FALSE` 為止。每次呼叫前都把 `DEVMODEW` 清零並重設 `dmSize`，理由與 `loadCurrentMode` 目前重設 `DmSize` 的理由相同：不假設 GDI 保留了呼叫者給的緩衝區大小。這純粹是讀取，任何時候執行都安全，不會改變任何顯示狀態，所以首次啟動流程可以毫無顧慮地用它。

`Controller` 介面因此多一個唯讀方法：

```go
EnumModes(target domain.Target) ([]domain.Mode, error)
```

驅動回傳的清單很長（數百筆很常見）而且很髒。過濾規則：

- `dmFields` 沒有宣告 `DM_PELSWIDTH | DM_PELSHEIGHT | DM_DISPLAYFREQUENCY | DM_BITSPERPEL` 整組四個欄位 → 丟棄。
- 寬、高為 0 → 丟棄。
- `dmDisplayFrequency` 為 0 或 1 → 丟棄（兩者都是「硬體預設」而非真實數值）。
- `dmDisplayFlags` 帶 `DM_INTERLACED` → 丟棄。工具不套用交錯模式。
- `dmBitsPerPel != 32` → 丟棄。工具只套用 32 bpp。若過濾後一筆不剩，視為「這台顯示器沒有可用模式」，設定流程對該顯示器中止並說明原因。

### 去重與排序

過濾後同一組 `(寬, 高, 刷新率)` 仍會重複出現多次——驅動會為不同的 `dmDisplayFixedOutput` 縮放變體各列一筆。去重鍵就是這三個值（色深已被釘在 32）。

排序是決定性的，不沿用驅動給的順序：解析度依像素數由大到小，像素數相同則依寬度由大到小；同一個解析度內的刷新率由高到低。

**目前模式一定在清單裡。** 以 `ENUM_CURRENT_SETTINGS` 另外讀一次，若它不在列舉結果中（自訂模式正在使用、或驅動把它從列舉中剪掉了），把它補進清單並標記為「目前模式」。不這麼做的話，使用者會看到一份不包含他眼前正在用的模式的清單。

### 刷新率

一個解析度常常提供好幾個刷新率（`1920×1440` 可能有 60 / 120 / 144 / 180）。把刷新率攤平到主清單會讓清單長四倍，而使用者要找的是「比例與大小」，不是刷新率。因此分兩層：

1. 先選解析度。主清單一列一個解析度。
2. 選定之後才出現該解析度的刷新率下拉選單，**預設選最高的那一個**，並在旁邊標出這個解析度總共提供幾個。

主清單的「最高刷新率」欄讓使用者不必展開就能比較。設定儲存的永遠是完整的 `(寬, 高, 刷新率, 32)` 四元組，不是「解析度 + 自動挑刷新率」——後者會讓同一份設定檔在驅動更新後套用到不同的模式。

### 呈現與長寬比

主清單是一個表格，欄位為 **解析度｜比例｜最高刷新率｜備註**，上方有一個「比例」篩選下拉（全部 / 4:3 / 16:9 / 16:10 / 其他），讓「我要找 4:3」變成兩次點擊而不是心算。

比例的算法是決定性的，沒有模糊比對：

1. 以 `gcd` 約分 `寬:高`。
2. 約分結果若命中已知表，顯示習慣寫法：`4:3`、`5:4`、`3:2`、`16:10`、`16:9`、`64:27` → `21:9`、`43:18` → `21:9`、`32:9`。
3. 否則，約分後的分母 ≤ 32 就直接顯示 `a:b`（例如 `256:135`）。
4. 否則顯示兩位小數的 `1.78:1`。`1366×768` 約分後是 `683:384`，這條規則讓它顯示成誠實的 `1.78:1` 而不是一串沒人看得懂的數字。

備註欄承載三件事：**目前模式**、**原生（列舉中像素數最大的）模式**，以及當所選模式的比例與原生模式不同時的一行提醒——「非原生比例，需要在顯示卡設定中啟用全螢幕縮放」。這是本設計與 GPU 縮放這個不在範圍內的主題唯一的接觸點：只提醒，不偵測、不設定。

清單在開啟設定對話框時與按下「重新整理」時重新列舉，結果在對話框存續期間快取。工具自己套用或恢復模式之後快取失效。更準的觸發點是主視窗收到 `WM_DISPLAYCHANGE`，值得做但不是第一版的必要條件。

### 後續階段：自訂（驅動未列舉的）解析度

**這一節描述的是之後的階段，第一版不實作。**

「顯示器列不出來的模式」要能用，路有兩條：

1. **使用者在顯示卡控制台或 CRU 之類的工具先建立它。** 建立完成之後，那個模式就會出現在 `EnumDisplaySettingsW` 的列舉結果裡，工具完全不需要任何新程式碼。**這是建議支援的路徑**，工具該做的只是在文件裡講清楚。
2. **工具自己合成時序並送給驅動。** 這需要顯示卡廠商的私有介面——NVIDIA 的 `NvAPI_DISP_TryCustomDisplay` / `NvAPI_DISP_SaveCustomDisplay`、AMD 的 ADL、Intel 各自一套。

第二條路的風險必須誠實列出來：

- **黑屏而且沒有退路。** Windows 設定 App 換模式時那個「15 秒內沒有確認就還原」的對話框是它自己實作的，不是 `ChangeDisplaySettingsExW` 附贈的。工具走的路徑沒有那一層保護，一個面板同步不了的時序就是一面黑螢幕加上使用者盲操作。這也正是「未解問題 6」提出的倒數確認機制的由來，而且那個機制對**任何**使用者自選模式都有價值，不只是自訂模式。
- **`CDS_TEST` 通過不代表面板會亮。** 前置驗證問的是驅動接不接受，不是顯示器同不同步。列舉出來的模式通過這一關的信心遠高於合成出來的。
- **`NvAPI_DISP_SaveCustomDisplay` 會在使用者系統上留下持久變更**，與「絕不把暫時的遊戲模式變成永久設定」直接衝突。
- **NVAPI 是未簽章的第三方 DLL 介面**，要嘛用 cgo，要嘛手寫 `LoadLibrary` + `nvapi_QueryInterface` 綁定。前者與 `CGO_ENABLED=0` 的硬約束衝突，後者是一大塊沒有型別安全的 `unsafe` 程式碼。
- 每一版顯示卡驅動對同一組自訂時序的接受度都可能不同，這是無法用單元測試覆蓋的。

建議：第一版只支援路徑 1，並且在自訂解析度真的要做之前，先把倒數確認機制做起來。

## 首次啟動流程

沒有設定檔就是首次啟動。

**啟動仍然什麼都不改。** 這條規則在首次啟動時同樣完整成立：偵測顯示器（`EnumDisplayDevicesW`）、列舉模式（`EnumDisplaySettingsW`）、列舉程序名稱（Toolhelp）全部是讀取。設定精靈裡**沒有任何動作會套用顯示模式**，連預覽都沒有（預覽見「未解問題 6」）。`CDS_TEST` 仍然只在使用者真的要套用的那一刻才跑。

使用者看到的是設定對話框以「初次設定」的標題直接開啟，三段內容，每段完成才解鎖下一段：

1. **選擇顯示器。** 清單顯示友善名稱、`\\.\DISPLAYn`、目前模式、是否為主要顯示器。兩台同型號會是兩列，各自帶著自己的介面路徑。
2. **選擇解析度。** 上一節描述的表格，範圍限定在第 1 步選的那台顯示器。
3. **選擇要觀察的程序。** 從 Toolhelp 快照取得目前執行中的程序**名稱**（去重、排序，附搜尋框），加上一個自由輸入欄。列的是名稱而不是路徑——這既維持了安全邊界（工具本來就只拿名稱），也讓「設定成路徑」這個錯誤幾乎不可能從 UI 產生。另有一個明確的「不觀察任何程序（只用手動切換）」選項。

按下**儲存**才寫檔，寫完之後關閉對話框，主視窗以與老使用者完全相同的狀態出現：什麼都沒套用，切換是關的。

**放棄首次設定不會留下任何檔案。** 「稍後再設定」把工具收進系統匣，切換停用並顯示原因「尚未設定」，系統匣選單多一個「設定…」。下一次啟動仍然是首次啟動。這是刻意的：一份半成品設定檔比沒有設定檔更難處理。

## UI 形狀

### 主視窗

維持刻意的精簡與固定尺寸。內容與現在一一對應，差別在於每一段文字都從 snapshot 產生，不再是 `internal/ui` 裡的常數（目前 `monitorName` 與 `toggleText` 都寫死了 Mi Monitor 與 `1920×1440 @ 180 Hz`）：

- 目標螢幕：`<設定中記下的名稱>` → `\\.\DISPLAY2`
- 目前模式：`2560 × 1440 @ 180 Hz（32 bpp）`
- 切換：`使用 1920 × 1440 @ 180 Hz（4:3）`  ← 文字由設定生成
- 自動恢復：`VALORANT-Win64-Shipping.exe，結束後 3 秒`，或 `未設定（不會自動恢復）`
- 狀態／錯誤訊息
- 按鈕：`設定…`｜`重新整理`｜`隱藏至系統匣`｜`恢復原始解析度`

尺寸從 `420×240` 放到大約 `460×280`，容納多出來的那一行與第四顆按鈕。若四顆按鈕在固定寬度下排不下，優先把「隱藏至系統匣」移到系統匣選單——關閉視窗與最小化本來就已經等同隱藏，那顆按鈕是三者中最可有可無的。

「恢復 2K」改名為「恢復原始解析度」，因為 `2560×1440` 不再是常數；按鈕的提示文字印出實際會套用的數字。

**留在主視窗外的東西：** 顯示器清單、模式清單、程序清單、任何需要捲動的內容、任何可編輯的欄位。主視窗回答「現在是什麼狀態、要不要切換」，不回答「我想改設定」。

### 設定是獨立視窗

是，而且**與首次啟動精靈是同一個對話框**，只有標題與步驟提示不同。一份程式碼、一套驗證規則、一條儲存路徑。模態、可調整大小（裡面有表格），約 `560×460`。

一條必要的互動規則：**工具正在管理已套用的模式時（`Session.managed` 為真），「設定…」停用**，原因寫在旁邊：「請先恢復原始解析度再變更設定」。中途換掉目標顯示器或目標模式，會讓 `Session` 保存的桌面排列對應到一個已經不存在的目標，恢復就會失效。停用是這裡唯一簡單而正確的規則。

### 系統匣

選單在分隔線之前多一項 `設定…`（與主視窗同樣的停用規則），其餘不變。提示文字（tooltip）帶上設定的顯示器與模式，讓使用者滑過圖示時就知道這份設定是哪一組。

所有字串維持繁體中文。

## 遷移

既有使用者（也就是這個工具的作者）沒有設定檔，而且期待內建的那組設定繼續運作。照「沒有檔案就是首次啟動」的字面規則，他會被推進一個他早就設定好的精靈。

採用**預填的首次啟動**，而不是靜默沿用：

- 首次啟動時，若 `MONITOR\XMI27B2` 對應的顯示器在線、且它列舉得出 `1920×1440 @ 180 Hz`，設定對話框開啟時三個欄位已經用舊的內建值填好，上方一行說明「偵測到既有設定，確認後儲存」。按一下儲存就得到他的設定檔。
- 那台顯示器不在線，就是一般的空白首次啟動。

**為什麼不直接靜默寫一份設定檔：** 在使用者沒有要求的情況下於第一次啟動就寫檔是個意外；而且萬一偵測錯了（前綴命中的是另一台同型號的機器），錯誤的身分就被寫死進檔案了。一次確認點擊很便宜。另一個被否決的方案是「沒有檔案時退回內建 profile」——那會讓「沒有檔案」在不同硬體上代表兩件不同的事，而且那台顯示器之後消失時的行為會變得難以解釋。（替代方案見「未解問題 2」。）

程式碼面的對應：`domain.DefaultProfile()` 不再是正式環境使用的 profile，降級為 `domain.LegacySeedProfile()`，唯一的用途是預填精靈。`cmd/resolution-tray/main_windows.go` 的組裝根從「建立 session」改成「載入設定 → 沒有設定就開精靈 → 有設定才建立 session」。

**降級執行**由版本規則涵蓋：舊版工具讀到 `version` 較新的檔案會拒絕並且不寫檔。因為現在要發佈的就是 `version: 1`，未來的 `version: 2` 必須保留讀取 v1 的能力。

## 與既有約束的新張力

一般化不會讓任何一條承諾失效，但它會把幾條原本罕見的路徑變成日常路徑。這裡列出來，是因為不列出來它們就會在使用者手上被發現。

- **`CDS_TEST` 從形式變成真的關卡。** 一個手挑出來、在該機器上驗證過的模式每次都會通過；使用者任選的模式不會。緩解有三層：以列舉清單取代自由輸入，讓多數壞選擇在事前就不可能；把 `CDS_TEST` 失敗做成一級的 UI 狀態而不是邊角情況（目前 `updateAvailability` 把它 latch 住，而且訊息裡寫死了 `1920×1440 @ 180 Hz`，必須改成由設定生成）；失敗本身不具破壞性——前置驗證在套用之前，這點不變。
- **模式現在會「變大」。** 舊的遊戲模式只會讓目標變窄（2560→1920）。使用者現在可能選一個比目前更寬或更高的模式，這會走進 `orderForApply` 的 `growsMode` 分支（先把鄰居移開，最後才套用目標模式）。那條分支有單元測試，但從來沒有在真實硬體上跑過。同時 `validateArrangement` 判定重疊而拒絕的機率顯著上升——拒絕是正確行為，但「算不出安全排列」會從理論上的錯誤訊息變成使用者真的會看到的訊息，它的措辭必須能指出是哪兩台螢幕會撞在一起。
- **`PlanModeChange` 的平移規則要在放大時重新檢視。** 它只平移座標嚴格大於目標的顯示器；縮小時這會把鄰居往目標拉近，放大時會把鄰居往外推。主要顯示器的回原點校正在放大時是往相反方向平移整個排列。邏輯本身對稱，但這是第一次真的被使用。
- **非原生比例不再能假設使用者做過設定。** README 目前把 NVIDIA 全螢幕縮放寫成一次性前置步驟。一般化之後工具無從得知使用者做了沒有，也不能替他做（明確不在範圍內）。能做的只有在挑選當下提醒，以及把 README 那一節從「請這樣設定」改成「若你選了非原生比例，你需要這樣設定」。
- **`ResolveTarget(prefix string) (Target, error)` 的簽章不再成立。** 它收一個字串前綴、回傳第一個命中。新的語意是收一個 `MonitorIdentity`、回傳恰好一個命中或一個歧義錯誤。這是整個設計中最大的一塊程式碼變更，而且會連帶影響 `internal/display` 的假實作與所有既有測試。
- **`Session.observed` 以 `mode == s.profile.GameMode` 計算 `FourByThree`。** 概念與名稱都要一般化（例如 `AtGameMode`），`Snapshot` 與 UI 的欄位名一起改。所有寫著「4:3」的固定字串改成由設定生成的文字。
- **`Profile` 是在 `NewSession` 時以值複製進 `Session` 的，而 `ui.Run(session)` 在整個程式生命週期持有同一個 `*app.Session`。** 執行期改設定因此不是改一個欄位那麼簡單。規則層面已經定好（管理中不得改設定），實作層面最乾淨的做法是儲存後重建 session，但那需要 UI 持有的是一個可替換的間接層而不是一個具體指標。（見「未解問題 9」。）
- **`internal/display` 的假 `user32` 測試會長大。** 新增的 `EnumModes` 與介面路徑列舉都要進去；現有那份假實作已經相當可觀，值得在加東西之前先把它整理成可組合的形狀。

## 錯誤與恢復（本設計新增的部分）

既有 spec 的錯誤清單全部保留。新增：

- 設定檔讀不懂：唯讀狀態，顯示路徑與確切錯誤（含行列），不寫檔，保留重新讀取／開資料夾／重新設定三個出口。
- 設定檔版本較新：唯讀狀態，明說原因，永不重寫。
- 找不到設定的顯示器：等同現有的 `ErrTargetNotFound` 路徑，設定檔保持原狀，重新整理是出路。
- 設定的顯示器命中多台（`ErrTargetAmbiguous`）：列出所有候選，請使用者重選，不動任何螢幕。
- 解析出的 adapter 同時驅動多台在線顯示器（複製／鏡射）：拒絕並說明工具無法單獨變更其中一台。
- 顯示器不再列舉得出設定的模式：停用切換並指向設定對話框；不改設定檔。
- 模式列舉失敗或過濾後為空：該顯示器在設定流程中不可選，並說明原因。
- 設定檔寫入失敗：保留使用者在對話框中的輸入不關閉，顯示錯誤；因為寫入是先寫暫存再 rename，舊設定檔一定完好。

## 測試策略

既有策略不變，新增的部分全部往「純函式優先」靠：

- **設定的解析與驗證是 `Parse([]byte) (Config, error)`**，測試永遠不碰磁碟。表格驅動涵蓋：合法檔、缺 `version`、`version` 較新、壞 JSON（並驗證行列換算）、負數與小數、超出範圍的 `restoreDelaySeconds`、`bitsPerPixel` 不是 32、空白的 `processName`、帶路徑的 `processName`、含非法字元的 `processName`、以及未知鍵被忽略。
- **原子寫入**針對暫存目錄測試：寫入後檔案內容正確、暫存檔不殘留、rename 前的中斷不會破壞既有檔案。並且斷言所有拒絕路徑都**沒有任何寫入**。
- **身分比對**是純函式，輸入是一份假的顯示器清單。涵蓋：主鍵命中、主鍵落空後次鍵唯一命中、次鍵命中多台、`ModelWasUnique = false` 時次鍵被停用、以及兩台同型號同時在線只命中被選的那一台。
- **模式列舉的過濾、去重與排序**是純函式，輸入是一批原始 `DEVMODEW`。涵蓋交錯模式、頻率 0 與 1、非 32 bpp、重複項、以及「目前模式不在列舉結果中要被補進去」。
- **長寬比標示**是純函式，表格驅動：`1920×1440` → `4:3`、`2560×1440` → `16:9`、`3440×1440` → `21:9`、`1280×1024` → `5:4`、`1366×768` → `1.78:1`。
- **設定路徑可注入**（`RESOLUTION_TRAY_CONFIG`），任何測試都不會讀寫使用者真正的 `%APPDATA%`。
- **Windows 整合測試**維持唯讀：模式列舉是安全的讀取，可以加進現有那支 opt-in 測試；`CDS_TEST` 以外仍然不得有任何會改變顯示狀態的呼叫，CI 永遠不設定 `RUN_DISPLAY_INTEGRATION`。
- **發布前人工 smoke test 新增兩項**：在第二台顯示器上完整走一次首次設定流程；以及選一個比目前更大的模式，確認 `growsMode` 的套用順序在真實硬體上不會讓桌面中途重疊。

## 已定案

作者已裁決的項目，取代下方對應的建議：

- **通用化範圍：** 顯示器、解析度、監測程序三者都可設定。設定存於 `%APPDATA%`，首次啟動走引導流程。
- **GPU 縮放：** 只實作 NVIDIA。偵測到 AMD 或 Intel 時停用按鈕並說明手動設定路徑，不假裝支援未經驗證的硬體。細節見另一份 NVAPI 規格。
- **未解問題 6（倒數確認）：** 延到自訂解析度那一階段，第一版不做。理由是第一版清單中的模式全部來自顯示器自己回報的列舉結果，`CDS_TEST` 通過後黑屏的機率低。代價已知並接受：屆時仍要為狀態機補上 `ConfirmPending` 與計時器，也就是核心狀態機會被改第二次。在自訂解析度落地之前不得移除這條備註。
- **未解問題 1、2、3、4、5、8、9：** 採用原建議。

## 未解問題

下列項目已由「已定案」裁決，保留原文以記錄當初的理由與被否決的替代方案。


1. **`%APPDATA%`（Roaming）還是 `%LOCALAPPDATA%`？** 顯示器身分是機器相關的，漫遊設定檔會把它帶到一台它毫無意義的機器上。
   *建議：* 照指示用 `%APPDATA%`。到了另一台機器只會走「找不到顯示器」那條已經設計好的安全路徑，不會造成損害。唯一會讓我改口的條件，是實際遇到網域漫遊使用者抱怨每換一台機器就要重選一次。

2. **遷移要預填確認，還是靜默沿用？**
   *建議：* 預填的首次啟動（本文採用）。靜默沿用只省一次點擊，卻讓「沒有設定檔」在不同硬體上代表兩件不同的事。若作者本人認為那次點擊不值得，替代方案是靜默寫入並在主視窗狀態列顯示一行「已沿用先前的內建設定」——但這個決定必須現在做，因為它決定了 v1 檔案是怎麼產生的。

3. **空的 `processName` 是合法的「手動模式」，還是應該直接拒絕？**
   *建議：* 合法，但在主視窗與系統匣提示中明講「自動恢復：未設定」。為一個選用欄位的空值拒絕整份檔案太重；真正的風險是使用者以為設了卻沒生效，而那是用顯示解決的，不是用拒絕解決的。

4. **次鍵重新對應成功之後，要不要把新的 `instancePath` 回寫進設定檔？**
   *建議：* 要，並在狀態列明講「已以硬體 ID 重新對應到 `\\.\DISPLAY3`」。這不牴觸「絕不重寫讀不懂的檔案」——那條規則講的是解析失敗的檔案，而這裡是解析成功加上一次無歧義的重新綁定。不回寫的話，使用者每次開機都要看一次同樣的重新對應訊息。反對意見是「任何未經使用者要求的寫入都是驚喜」；若採納這個意見，就改成在狀態列提供一顆「記住這個對應」。

5. **友善名稱要不要走 CCD API？** `EnumDisplayDevicesW` 給的 `DeviceString` 常常是「Generic PnP Monitor」，對設定清單幫助有限。`GetDisplayConfigBufferSizes` + `QueryDisplayConfig` + `DisplayConfigGetDeviceInfo(DISPLAYCONFIG_DEVICE_INFO_GET_TARGET_NAME)` 能拿到真正的機型名稱。
   *建議：* 做，唯讀，且失敗時安靜退回 `DeviceString`，再退回硬體 ID。多一塊 Win32 介面換來的是使用者真的認得出自己那台螢幕——在一份「挑錯就把模式套到別台螢幕」的清單裡，這個交換划算。

6. **要不要為套用加上倒數確認（「保留這個模式嗎？15 秒後自動還原」）？** 這會讓狀態機多一個 `ConfirmPending` 狀態與一個計時器。
   *建議：* 做，而且第一版就做。`CDS_TEST` 通過但面板同步不了的模式會給使用者一面黑螢幕，而使用者現在可以自己挑模式，這個情境從「不會發生」變成「遲早會發生」。它同時也是自訂解析度將來能不能做的前提。這是本清單中唯一一個會改變核心狀態機的問題，所以必須現在決定，不能留到之後補。

7. **兩台同型號顯示器，要不要用 EDID 序號當第三層辨識？** 需要讀 `HKLM\SYSTEM\CurrentControlSet\Enum\DISPLAY\...\Device Parameters\EDID` 並解析。
   *建議：* 第二階段，而且只在「以輸出埠為基礎的介面路徑」被實際證明不夠用之後才做。理由是不少顯示器的 EDID 序號欄位是空的、或同型號全部相同，做了不一定救得到，而換線這個觸發條件本身並不常見。

8. **v1 要不要先把 profile 包成清單，為多組 profile 預留？**
   *建議：* 不要。v1 就是單一 profile，未來的多 profile 是 `version: 2`，並把 v1 檔案讀成只有一個元素的清單。版本機制存在的意義就是讓現在不必為猜測中的需求把 schema 弄複雜。

9. **設定變更之後，要重建 `Session` 還是就地更新它？** 這會影響 `ui.Run` 的簽章——目前它收一個 `*app.Session` 並持有到程式結束。
   *建議：* 重建。`Session` 持有的保存排列、擁有權旗標與觀察 goroutine 全部是綁在某一組 profile 上的，就地更新等於要逐一想清楚每一個欄位在切換瞬間的正確值。改成 UI 持有一個可替換的 session 提供者，並沿用「管理中不得改設定」這條規則，把重建限制在沒有任何東西需要恢復的時刻。
